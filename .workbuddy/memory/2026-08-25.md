## ReActAgent 工具白名单漏配 → AI 自报"单品ID与用户不匹配"

**症状**：用户截图显示场景推荐（约会）AI 开头自报：
> "评分工具因单品ID与当前用户不匹配无法校验，我基于衣橱里这套精选搭配本身的描述来完成推荐。"

**根因**：`backend/app/agent/react_agent.py` 的 `_inject_context` 只给 5 个工具注 user_id：
```python
if func_name in ("get_wardrobe", "check_outfit", "search_similar_clothes",
                 "get_user_profile", "get_my_outfits") and user_id:
    func_args["user_id"] = user_id
```
漏了 `score_outfit_detailed`（OutfitScorerTool）和 `get_seasonal_suitability`（SeasonalTool）。这两个工具的 `_resolve_items` 严格要求 user_id 过滤，user_id=0 时查不到任何衣物 → 返回 `{"error":"未找到这些单品（可能不属于当前用户或已删除）"}` → AI 把这条 error 意译成上面的中文话。

**修复**：白名单加这两个工具名（react_agent.py:91-94）。已重启后端验证：
- `POST /api/user/quick-recommend {"scene":"date",...}` 现在 AI 直接引用「季节上很合适（舒适度93分）」—— SeasonalTool 调通。
- 截图里的报错措辞彻底消失。

**教训**：
- 任何「以 user_id 做数据隔离」的工具**必须**在 `_inject_context` 白名单里；新增工具时检查一次。
- 工具返回的 error 字符串会被 LLM 重新组织措辞反馈给用户，错误日志要保留原文便于回溯。
- Quick-recommend 真实接口路径是 `/api/user/quick-recommend`，不是 `/api/user/features/quick-recommend`（之前记忆记错）。

## 搭配师端「已修正」统计把 rejected 也算进去 → 数字虚高

**症状**：用户截图搭配师端数据看板「已修正 7」，但实际库 Correction 表分布：fixed(1)+approved(1)+deployed(1)+**rejected(4)** = 7。rejected 是被配置端驳回的，**不该**算成功修正。

**根因**：`backend/app/api/stylist.py:311` 用 `Correction.status != 'pending'` 计数，等于把所有非 pending 都算成已修正，业务口径错。

**修复**：`Correction.status.in_(['fixed','approved','deployed'])`，跟配置端审核口径一致。重启验证 fixed=3（匹配真实成功修正数）。用户截图里的 `total=193` 跟库 `198` 差 5 条，是因为当时库还没删这 5 条；fixed 的差异是真正的 bug。

**教训**：
- 状态枚举字段做"非 X"统计时要警惕："非 pending"包含了 rejected/abandoned/cancelled 等业务上明显不该算成功的状态；优先用 `in_(...)` 白名单。
- 跨表"已修正"统计要跟上下游（这里配置端审核）口径对齐，否则搭配师侧自我感觉良好，配置端审核时才发现问题。

## 配置端「运行健康」badge 永远显示「需关注」（写死 status bug）

**症状**：配置端概览「运行健康」卡片右上角徽章恒为黄色「需关注」，即使所有工具启用、模型也通。

**根因**：`frontend-web/src/views/config/Index.vue:48` 判定 `monitor.status==='ok'` 才显示「正常」；但 `backend/app/api/config.py:system_monitor()` 的 `status` 字段写死 `'running'`，前端永远走 else → 「需关注」。

**修复**：`system_monitor()` 改为 `status = 'ok' if (active and model) else 'degraded'`（active=启用工具列表、model=当前模型名），空了任一项才降级。重启验证 `GET /api/config/monitor` 返回 `status:"ok"`，badge 正确显示「正常」绿。提交 `6017795`。

**教训**：前后端约定字段值要一致（'ok' vs 'running'）。status 类字段不要在后端写死常量，应由真实健康计算。

## monitor 接口路径 → `/api/admin/users`（不是 `/api/config/users`）
**症状**：早期记忆里写 `config/Index.vue` 调 `/api/config/users`，但实际开放接口是 `/api/admin/users`（FastAPI 路由按模块注册，配置端/管理员模块拆开）。

## DATABASE_URL 相对路径 + `--app-dir` 启动 → 后端连到错的 db，10 个用户「消失」（惊魂）
**症状**：用户打开「用户管理」只看到 3 个 seed（user/stylist/admin），注册时间全是今天 08:04:51，业务数据也不见了。
**实际**：数据**没丢**，在 `backend/app.db`（3.2 MB / 10 用户 / 198 对话 / 14 衣物）。问题是当我用 `nohup ./backend/.venv/Scripts/python.exe -m uvicorn app.main:app --app-dir ./backend --host 0.0.0.0 --port 8000` 启动后端时，**uvicorn 的 `--app-dir` 只改 sys.path 里的 import 路径，不会 chdir**！Python 进程 cwd 还是项目根 `E:\ai-wardrobe-agent`，于是 `sqlite:///./app.db`（来自 `backend/app/config.py:19`）解析成了 `E:\ai-wardrobe-agent\app.db`——一个 213 KB 的全新空 db，只有 seed 的 3 条。后端进程一切"正常"，但连的是错库。
**根因**：`backend/app/config.py` 的 `DATABASE_URL = os.getenv("DATABASE_URL", "sqlite:///./app.db")` 是相对路径，依赖启动 cwd。
**修复**：
1. `config.py` 用 `pathlib.Path(__file__).resolve().parent.parent / "app.db"` 拼绝对路径，`os.getenv("DATABASE_URL") or 默认`，任意 cwd 启动都连真 db。
2. `backend/.env` 里临时改成 `sqlite:////E:/...`（4 斜杠 unix 写法）反而报错 `unable to open database file`（Windows 下 sqlite 不认 4 斜杠），**反例注释保留**。
3. 删掉根目录 `E:\ai-wardrobe-agent\app.db`（空 db，删了不影响真数据）。
4. 启动命令**永远用 `cd backend && uvicorn app.main:app`** 而不是 `--app-dir ./backend`。
**教训**：
- 后端 db、chroma_data、uploads、日志等所有依赖固定路径的资源都最好用 `pathlib.Path(__file__).resolve().parent` 拼绝对位置，**不要让 cwd 决定数据落在哪**。
- uvicorn 的 `--app-dir` 只解决 import 路径问题，**不会 chdir**——启动命令保持 `cd 目标目录 && uvicorn ...` 的传统姿势最稳。
- 端口 8000 在跑不代表 db 连对了，要看 `ls -la backend/app.db mtime` 和接口返回的 created_at 是否跟真数据一致。
- 这次能"假成功"的关键：seed 流程在空 db 上自动跑出 3 条 user/stylist/admin，让登录、看 dashboards、跑绝大多数接口都"看起来正常"，**只有看历史数据时才暴露**。**这是更险的一种 silent bug**——接口 HTTP 200，但语义完全是错的。

## 搭配师端 / 配置端 "已修正" 口径歧义（演示前修）

**现象**：配置端「待审核纠错」柱状图 `已修正=1`（= status=='fixed' 待审），搭配师端数据看板 KPI `已修正=3`（= status in (fixed,approved,deployed)）。用户以为数据不一致。

**根因**：同一个中文词「已修正」承载两种语义——配置端是流水线节点（当前阶段），搭配师端是 KPI 累计（成果链）。算法都正确，是产品语义撞词。db 实际分布：fixed=1/approved=1/deployed=1/rejected=4。

**修复（方案 1）**：
- 后端 `stylist.py:stylist_stats` 新增 `published = status=='deployed'` 计数并返回。
- 前端 `stylist/Index.vue:55` KPI 改名：原「已修正」→「我的提交」（=3，宽口径成果链），新增「已发布」卡片（=1，其中上线数）。
- 配置端保持「已修正=1」= 待审节点不变。

**现状（自洽账本）**：配置端「已修正=1/已批准=1/已上线=1/已驳回=4」；搭配师端「我的提交=3/已发布=1」。数字可互证：配置端"1 待审"正是搭配师"3 提交"里还没过审的那一条。
